# CertScope

CertScope is a browser-based X.509 / PKCS#10 inspector. It parses certificates,
CSRs, and CRLs entirely in the browser and can validate certificate chains and
signatures using the Web Crypto API.

Built with React + TypeScript + Vite.

## Commands

Install dependencies (from a clean checkout):

```bash
npm install
```

| Command | Description |
| --- | --- |
| `npm run dev` | Start the Vite dev server with HMR. |
| `npm run build` | Type-check the project (`tsc -b`) and produce a production build in `dist/`. |
| `npm run check` | Run the TypeScript type checker without emitting output. |
| `npm test` | Run the Vitest suite once (CI-friendly). |
| `npm run lint` | Run ESLint over the project. |

### Testing

Tests use [Vitest](https://vitest.dev). They run against the **same TypeScript
sources** that the browser app imports (via the `@/` alias), so there is no
separate compilation step, no native `.ts` execution, no custom loader, and no
dependency on a specific working directory:

```bash
npm test
```

`npm test` works immediately after a fresh `npm install` (or `npm ci`).

Test coverage includes:

- **ASN.1 length parsing** (`test/asn1.test.ts`) — DER short-form, long-form
  (`0x81`/`0x82`) lengths, and rejection of indefinite/overrun/truncated
  lengths.
- **X.509 fields** (`test/x509.test.ts`) — certificate subject, issuer,
  validity period, and serial number.
- **Certificate details** (`test/certDetails.test.ts`) — the resilient
  `describeCertificate*` core used by the details page: a normal certificate,
  an expired certificate (validity checked against an injected time), and
  corrupted input (returns an error, never throws). Expected values are pinned
  to OpenSSL output / fixture notes, not generated by the parser under test.
- **Validity check** (`test/certDetails.test.ts`) — `checkValidity` across all
  three states (not-yet-valid / valid / expired) with day counts, exact
  boundary behavior, determinism (identical input + evaluation time ⇒ identical
  result), and time-zone boundary handling (the same instant expressed with
  different UTC offsets yields the same result; an offset that crosses a
  boundary flips the state).
- **Certificate validity** — the chain validator takes the verification time as
  a parameter (`validateChain(chain, crls, verificationTime)`), and
  `getValidityStatus(summary, verificationTime)` / `checkValidity(summary,
  verificationTime)` likewise take an explicit time, so validity tests pin a
  fixed date and never depend on the current day.
- **CSR basic fields** (`test/csr.test.ts`) — PKCS#10 version, subject DN, and
  SubjectPublicKeyInfo algorithm.

## Certificate details page

The **证书详情 (Certificate Details)** tab renders a resilient summary of a
certificate — serial number, subject, issuer, validity period, public-key
algorithm, signature algorithm, and common extensions. Parsing is handled by
the pure, never-throwing core in `src/utils/certDetails.ts`
(`describeCertificateFromPEM` / `describeCertificateFromDER`), so malformed or
corrupted input shows a clear error message instead of crashing the page.

### Validity check

The page includes a simple validity check. You choose an **evaluation time**
(interpreted as UTC), and the page clearly shows one of three states —
**尚未生效 (not yet valid)**, **当前有效 (currently valid)**, or **已经过期
(expired)** — along with the number of days until it becomes valid / until it
expires / since it expired. The computation (`checkValidity` in
`src/utils/certDetails.ts`) is pure and uses absolute UTC timestamps, so the
same certificate and evaluation time always produce the same result. The last
evaluated certificate, evaluation time, and result are persisted to
`localStorage` and restored after a page refresh.

## Test fixtures

Test certificates live in `test/fixtures/certs/`. They are **public-key material
only — no private keys are included**:

| Fixture | Description |
| --- | --- |
| `root-cert.pem` | Self-signed test Root CA certificate. |
| `leaf-cert.pem` | Leaf/end-entity certificate (`CN = test.example.com`) issued under the test PKI. |
| `leaf-csr.pem` | PKCS#10 certificate signing request for the leaf subject. |
| `expired-cert.pem` | Self-signed certificate (`CN = expired.example.com`) with a fixed, already-past validity window (`2020-01-01` → `2020-01-02`), used to test expiry independent of the current date. |

### Provenance

These fixtures were generated locally with OpenSSL as a self-contained test PKI
(Root CA → Intermediate CA → leaf) and copied into `test/fixtures/certs/` from
the repository's `test-certs/` working directory. `expired-cert.pem` was
generated separately with a pinned validity window
(`openssl req -x509 ... -not_before 20200101000000Z -not_after 20200102000000Z`)
and only its certificate — never the private key — was kept. They contain no
real-world or sensitive data, and the corresponding private keys are
intentionally **not** committed to the fixture set. Expected values in the tests
(subjects, issuers, validity windows, serial numbers, key/signature algorithms)
are pinned to the `openssl x509` / `openssl req` output for each file.
